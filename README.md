# 📈 科技產業情報與財報｜混合架構 RAG 智慧問答 Agent

同一份財報資料庫與文件庫，兩種做法：

- **v2（目前版本）**：資料層包成 **FastAPI** 服務，Agent 以手寫的 **Gemini Function Calling** 迴圈呼叫 5 個工具，再加上一組以程式實作的防護層與一套可重複執行的評估腳本。
- **v1**：Router 判斷路徑 → Text-to-SQL 或 RAG，Streamlit 介面。內容保留在下方，v2 沿用其資料清洗與文件檢索。

> v2 還沒有與 v1 在同一組問題上做對照評估，因此本文不主張 v2「比 v1 準」，只說明它的設計與實測結果。

# v2：API 化 + Function Calling Agent

## 架構

```mermaid
flowchart TD
    Q[使用者問題] --> L["Agent 迴圈 loop.py<br/>Gemini Function Calling・最多 6 輪"]
    L -->|呼叫工具| T["tools.py<br/>5 個工具・逾時・錯誤回報"]
    T -->|HTTP| API[FastAPI api/main.py]
    API --> S[service.py 商業邏輯]
    S --> DB[("SQLite 唯讀・v_financials")]
    API --> D["documents.py 文件檢索<br/>延遲載入・可選依賴"]
    D --> C[(ChromaDB)]
    L --> G{"防護層（程式實作）"}
    G -->|未溯源數字・股票代號| N[提醒後重試一次]
    G -->|答案複述系統提示| R[替換成固定拒絕訊息]
    G -->|Gemini 回傳空白| E[降低溫度重試]
```

分層：`endpoint（main.py）→ 商業邏輯（service.py）→ 資料存取（db.py / documents.py）`。AI 層只透過 HTTP 呼叫 API，因此資料 API 可以不接任何 LLM 單獨測試。

| 工具 | 對應 API | 用途 |
|---|---|---|
| `search_company` | `/companies` | 公司名、暱稱、代號 → 股票代號 |
| `get_financials` | `/financials` | 某公司某科目的各期數字 |
| `get_ranking` | `/rankings` | 某期某科目的排名（可限定產業）|
| `get_ratio` | `/ratios` | 毛利率、營業利益率、營業費用率（含摘要）|
| `search_documents` | `/documents/search` | 在年報與法說會中找「為什麼／怎麼看」的段落 |

## 設計決策

- **手寫 tool calling，不用 LangChain**：每一步可記錄、可限制輪數、可在中間插入防護。關閉 SDK 的自動函式執行。
- **API 契約明確**：參數以 Pydantic 與 `Query` 驗證；缺資料時以 `missing_companies`、`skipped_periods` 明講，不靜默略過；文件檢索「沒有相關段落」回 **200 + 空陣列**，不是 404，並附 `coverage` 與 `note`。
- **向量庫是可選依賴**：載入失敗時 `/documents/search` 回 503，財報 API 不受影響。
- **文件檢索按公司過濾**：向量相似度分不出問題在問哪家公司。實測問「聯發科毛利率為什麼下降」曾回傳 2 段台積電的 Q&A，因此 `company` 參數先對應到有文件的公司，沒有就直接回空並說明文件庫涵蓋範圍。
- **數字題先查數字，再查原因**：「為什麼」類問題先用財報確認前提是否成立（含文件庫沒有的公司），再去文件找原因。
- **API 金鑰驗證與限流**（`api/security.py`）：預設拒絕（沒設 `API_KEY` 就不啟動）、金鑰可多把以便輪替、固定時間比對、金鑰不進日誌；限流依「驗證過的金鑰」計算（容器與反向代理後面看不出真實 IP），`/documents/search` 每次都會呼叫 Gemini，因此另有更緊的額度。工具層遇到 401／429 時只給模型中性訊息，不交出驗證細節。測試會檢查「每個端點（除 `/health`）都有驗證」，新增端點忘了加會失敗。
- **啟動時檢查工具宣告**：確認每個工具對應的路徑真的存在於 API 的 `/openapi.json`，避免 API 改版後工具沒跟上。

### 防護層（全部在程式端，不依賴提示詞）

| 防護 | 做法 |
|---|---|
| 沒查資料就報數字 | 答案含數字或股票代號、卻沒呼叫任何工具 → 提醒一次，仍不行就拒絕 |
| 系統提示洩漏 | 兩層過濾：與系統提示有 25 字元以上重疊；或答案同時出現 2 個以上內部識別字（函式名、欄位名）|
| 「文件庫沒有資料」但沒搜過 | 其他工具已被呼叫、卻沒呼叫 `search_documents` 就宣稱沒有 → 提醒一次 |
| Gemini 回傳空白 | 以 temperature 0.3、再 0.7 重試，次數列入評估指標 |

洩漏防護原本寫在提示詞裡（規則 9），結果造成無關問題出現空白回覆，移除後改為純程式端過濾。

## 評估

評估腳本（`agent_v2/eval.py`）：

- 標準答案**由 API 即時產生**，不手抄數字；每題重複執行多次。
- 檢查項目：必須／禁止呼叫的工具、答案必須包含的事實、禁止出現的文字與數字、引用格式。
- 區分**開發集**（看過結果後調整過）與**留存集**（調整完才跑一次）。
- 若系統提示中出現任何測試題文字，評估直接中止（防止把測試題寫進提示詞）。

| 題組 | 題數 × 次數 | 結果 | 性質 |
|---|---|---|---|
| 財報核心題 | 15 × 5 | 72/75（97%）| 開發集 |
| 財報留存集 | 10 × 5 | 45/50 | 只跑一次；唯一的失敗是系統提示洩漏，之後已用程式修正，未重跑 |
| 文件題 | 5 × 5 | 25/25 | 開發集 |
| 文件題留存集 | 6 × 5 | 30/30 | 只跑一次，之後的程式修改未重跑 |
| 提示詞注入 | 7 × 5 | 30/35 | 開發集；`i_translate` 0/5 尚未解決（模型把問題原文回聲，既沒洩漏也沒拒絕）|

注入題中，程式端攔截了 23 次洩漏，沒有任何一題出現洩漏標記詞。

### 過程中發現並修正的問題

- **「數字 + 原因」題整題放棄**：缺少比率工具，模型找不到合適工具就不答 → 新增 `get_ratio`。
- **沒呼叫工具就報數字**（幻覺）→ 數字溯源保險；之後延伸到股票代號。
- **提示詞規則造成連帶失效**：新增規則 9 之後，比率類問題出現空白回覆。我一開始只還原了規則的措辭、沒有回到真正的基準，診斷後才確定要整條移除。
- **提示詞範例洩漏測試題**：規則 6 的範例和測試題文字相同 → 改成通用描述，並讓評估腳本偵測並中止。
- **評分器本身的瑕疵**：引用檢查把「A、B」連寫的合法引用判成捏造 → 修正切分邏輯。

## 啟動 v2（macOS）

先在 `.env` 加上 API 金鑰（至少 16 字元），服務端與 Agent 共用：

```bash
printf '\nAPI_KEY=%s\n' "$(python -c 'import secrets; print(secrets.token_urlsafe(32))')" >> .env
```

本機開發若想略過驗證，須明確設 `AUTH_DISABLED=1`；沒設任何一個，API 會拒絕啟動。

```bash
# 終端機 1：資料 API（互動文件在 http://127.0.0.1:8000/docs）
uvicorn api.main:app --reload

# 終端機 2：問一個問題
python -m agent_v2.loop "台積電 2025 年各季毛利率趨勢？"

# 評估（每次都會呼叫 Gemini 並計費，先用 --runs 1）
python -m agent_v2.eval --set core --runs 1
python -m agent_v2.eval --set docs --runs 1
```

評估結果（含每次的完整答案與 token 用量）存在 `eval_results/`。

## v2 已知限制

- **引用只驗證「來源存在」，不驗證「來源支持該句話」**；許多引用只到文件層級。
- **洩漏過濾抓不到不含內部名稱的改寫**。
- **Gemini 偶發回傳空白**，以重試緩解，根因未明，重試也不保證成功（核心題 5 次中有 1 題曾兩次重試仍空白）。
- 限流狀態存在記憶體：單一 worker 準確，多 worker 時實際上限會乘上 worker 數（精確限流需共用儲存，如 Redis）。
- 尚未加 HTTPS：金鑰在明文連線上傳送，真正對外開放前必須放在帶 TLS 的反向代理後面；`/openapi.json` 與 `/docs` 目前是公開的。
- 股票代號若不加括號寫在答案裡，數字溯源保險不會檢查到。
- 文件檢索只涵蓋台積電；沒有多輪對話記憶；回答偏長，沒有長度規則。
- 資料品質：10 家公司缺 2025Q4 營收；17 筆毛利與（營收 − 成本）不一致（皆為光寶）；與官方數字的核對只做了台積電。
- 法說會逐字稿有編碼亂碼，需重建向量庫才能修正。
- 核心題在看過結果後調整過，有過度擬合的風險；留存集的樣本也很小。

# v1：Router 混合架構（Streamlit）

結合 **Text-to-SQL** 與 **RAG（檢索增強生成）** 的問答系統。使用者用自然語言提問，系統自動判斷問題類型：數字題查詢財報資料庫，觀點題檢索台積電年報與法說會，需要「數字 + 原因」的問題則兩條路同時執行，最後產生**附有引用來源**的中文回答。

![系統畫面](docs/screenshot.png)

---

## ✨ 功能特色

- **自動路由**：LLM 以結構化輸出判斷問題該走資料庫、文件庫、兩者並用，或超出範圍
- **Text-to-SQL**：自然語言轉 SQL，含四層安全防護與自我修正機制
- **RAG 檢索**：解析多欄排版 PDF 與中英對照逐字稿，回答時逐句標註引用來源
- **平行執行**：需要兩條路徑的問題同時查詢，總耗時取決於較慢的一條
- **透明可追溯**：介面可展開查看路由判斷、各階段耗時、實際執行的 SQL

### 可以問的問題

| 類型 | 範例 | 路由 |
|---|---|---|
| 財報數字 | 台積電 2025 年各季的營收？ | 📊 資料庫 |
| 排名比較 | 2025Q4 毛利率最高的前五家公司 | 📊 資料庫 |
| 經營觀點 | 台積電怎麼看 AI 需求？ | 📚 文件庫 |
| 數字 + 原因 | 台積電毛利率為什麼一直上升？ | 📊 + 📚 兩者並用 |

### 資料管線

```
上游 ETL 專案（MOPS 爬蟲）──唯讀快照──→ finance_raw.db ──清洗──→ finance.db ──→ Text-to-SQL
年報 PDF・法說會逐字稿 ──解析──→ 切塊 ──Gemini Embedding──→ ChromaDB ──→ RAG
```

財報資料由另一個 ETL 專案負責抓取與入庫，本專案以 SQLite backup API 取得**唯讀快照**，避免與上游的寫入衝突，兩個專案可以獨立開發。

## 🔍 開發過程中解決的關鍵問題

這個專案大部分的工作不在「串接 API」，而在**發現並修正資料與模型的錯誤**。以下是幾個代表性的問題。

### 1. 財報資料稽核：MOPS 的 Q4 是全年累計值

接上 Agent 之前，先對上游資料做稽核，發現：

| 問題 | 影響 | 處理方式 |
|---|---|---|
| 損益表 Q4 為**全年累計** | 台積電 Q4 營收被誇大約 4 倍 | Q4 = 全年 − Q1 − Q2 − Q3 |
| 現金流量表**每季皆為年初累計** | 各季數字都不是單季 | 單季 = 本季累計 − 上季累計 |
| 部分科目對應錯誤（稅前淨利、稅後淨利、投資現金流）| 回答會出現錯誤數字 | 以**白名單 + View** 隔離，只開放驗證過的 14 個科目 |
| LLM 產生的公司名稱有幻覺（兩家公司都叫「長榮海運」）| 公司對應錯誤 | 人工修正 |

依「流量 vs. 存量」區分處理方式：資產負債表為時點數字不需還原，損益表與現金流量表需依各自的累計方式還原。還原後以台積電官方公布數字驗證：

| 項目 | 系統計算 | 官方公布 |
|---|---|---|
| 2025Q4 營收 | 新台幣 1,046,090 百萬元 | 新台幣 1,046,090 百萬元 |
| 2025Q4 EPS | 19.51 元 | 19.50 元（四捨五入差異）|
| 2025 各季毛利率 | 58.8% / 58.6% / 59.5% / 62.3% | 一致 |

### 2. Text-to-SQL：四層安全防護

LLM 產生的 SQL 屬於不受信任的程式碼，採用**縱深防禦**：

1. **Prompt**：規定只能使用 SELECT
2. **程式檢查**：只允許 `SELECT` / `WITH` 開頭、單一指令、禁止 `DROP`、`DELETE` 等關鍵字
3. **資料庫權限**：以唯讀模式（`mode=ro`）連線，即使前兩層被繞過，資料庫本身也會拒絕寫入
4. **結果上限**：最多回傳 200 筆

另有**自我修正迴圈**：SQL 執行錯誤時，把錯誤訊息回饋給 LLM 重寫（最多 2 次）；但**安全檢查未通過的請求絕不重試**，避免給注入攻擊更多嘗試機會。

### 3. 多欄排版 PDF：文字順序錯亂

年報為左右分欄排版，一般擷取方式會逐行橫向讀取，導致左右欄的句子交錯。解法：

- 依文字區塊的 X 座標**自動偵測欄數**（致股東報告書每頁 2 欄、營運概況每頁 4 欄）
- 先依欄位、再由上往下排序
- 以**行距分布**判斷段落邊界：量測後發現段落內行距為 4～5pt、段落間為 11pt 以上，取 8pt 為門檻

### 4. 法說會切塊：提問與回答被拆開

最初以「發言者」為單位切塊，結果分析師的提問與管理層的回答被分到不同的塊，檢索時只找到問題、找不到答案。

- 第一版改用「管理層回答後分析師再發言就分組」，但實測發現**分析師的道謝會誤觸發分組**，且**主持人有時也會直接回答問題**
- 最終改為**以分析師為單位分組**，被拆開的塊會在開頭補上該分析師「最近一次」的提問，讓每一塊都能獨立被理解

### 5. 檢索優化：來源多樣性與相關性門檻

- **多樣性**：初版前 3 名全部來自同一份逐字稿，年報的長期觀點被擠掉。改為先取 15 個候選、每份文件最多 2 段，再取前 5 段
- **門檻**：向量檢索一定會回傳結果，即使問題無關。以實驗決定門檻：

| 類別 | 相似度範圍 |
|---|---|
| 相關問題（AI 需求、2 奈米、亞利桑那擴廠、CoWoS）| 0.696 ～ 0.798 |
| 無關問題（天氣、電影）| 0.539 ～ 0.609 |

  取 **0.65** 為門檻。實驗中「員工餐廳好吃嗎」得到 0.691，查證後發現年報確實提到「各廠區提供員工餐廳」，屬於**部分可回答**的問題，系統會回答「有員工餐廳，但資料未提及餐點品質」。

### 6. 引用驗證：錯誤的源頭是第三方翻譯

逐句抽查回答時，發現 AI 加速器 CAGR 被寫成「朝向 50% 的高端」，原文為 *"toward higher 50s"*（50 幾 % 的高段）。追查後確認**錯誤來自第三方逐字稿的中文翻譯本身**，而非 LLM。因此規定數字以英文原文為準，並在回答中附上原文。

其他引用相關的保護機制：
- 程式驗證引用編號，刪除不存在的編號（例如只有 4 段卻引用 [6]）
- 引用清單由程式產生，只列出實際被引用的來源
- 「資料中沒有提到」的句子，由程式移除其引用編號

### 7. Router 評估：避免資料洩漏

以 17 題測試集評估路由準確率（**17/17**）。初版 12 題中有數題與 Prompt 範例幾乎相同，屬於**資料洩漏**，因此另外加入 5 題未出現在 Prompt 中的困難題（口語化說法、非台積電公司的觀點題、美股公司等）。

評估時也發現：**路由正確不代表輸出正確**。「聯電營收是不是比去年差」路由正確，但子問題被換算成錯誤的年份。修正方式是讓 Router 保留原始的時間說法，由知道資料範圍的 Text-to-SQL 負責換算。

```bash
git clone https://github.com/eric87911/tech-rag-agent.git
cd tech-rag-agent
python -m venv .venv
.venv\Scripts\Activate.ps1        # Windows PowerShell

### 2. 設定環境變數

複製 `.env.example` 為 `.env`，填入：

```
GEMINI_API_KEY=你的 Gemini API Key
GEMINI_MODEL=gemini-2.5-flash
EMBED_MODEL=gemini-embedding-001

本專案的資料**不包含在儲存庫中**：

- **財報資料庫**：由另一個 MOPS 爬蟲 ETL 專案產生，路徑設定於 `SOURCE_DB`

streamlit run app.py

## ⚠️ 已知限制

- **財報資料截至 2025Q4**：上游使用的舊版 MOPS 網站無法解析 2026 年的新版 XBRL Taxonomy，2026 年資料暫不開放
- **兩條路徑的時間範圍不一致**：財報數字截至 2025Q4，法說會逐字稿為 2026Q1，`both` 類問題的兩段回答可能談的是不同期間
- **文件僅涵蓋台積電**：其他公司的觀點類問題會被判斷為超出範圍
- **逐字稿為第三方整理**：中文翻譯可能有誤，數字以英文原文為準；檔案受版權限制，不包含在儲存庫中
- **沒有對話記憶**：每個問題獨立處理，無法理解「那聯電呢？」這類追問
- **評估樣本有限**：檢索門檻以 7 題、路由以 17 題評估，尚需更大的評估集
